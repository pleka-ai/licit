Cómo funciona_

Toda la contratación pública española desde 2017, buscable por API y consultable con SQL, sin un solo servidor encendido y sin coste recurrente. Cada pieza corre donde sale más barato y más rápido: GitHub procesa, Cloudflare sirve y tu navegador analiza.

El viaje de un dato

  1. 1

    La PLACSP publica

    La Plataforma de Contratación del Sector Público expone feeds ATOM en formato CODICE, paginados y sin filtros, y un archivo ZIP por año. Es la única fuente: licit no inventa ni enriquece datos.

  2. 2

    GitHub Actions procesa

    Cada madrugada se levanta un Postgres de usar y tirar dentro de GitHub Actions. Restaura el estado del día anterior desde R2, lee las páginas nuevas del feed con el ETL en Python, normaliza códigos CODICE a etiquetas y poda lo que tiene más de dos años. Al acabar, guarda el nuevo estado y el contenedor desaparece.

  3. 3

    DuckDB transforma

    DuckDB fusiona el histórico con lo nuevo en un único Parquet sin duplicados, ordenado por fecha, y calcula las tablas derivadas (empresas, órganos, catálogos, resúmenes). Lo que en la base de datos de la API tardaría más de 30 s, aquí tarda menos de un segundo.

  4. 4

    Cloudflare guarda

    Los cambios del día llegan a D1 (SQLite gestionado) como upserts que nunca pisan una versión más nueva. Los Parquet y el estado se suben a R2. Si D1 se acerca al almacenamiento incluido en el plan, el proceso falla a propósito y avisa.

  5. 5

    El Worker sirve

    Un único Worker atiende licit.es y api.licit.es: la web estática, la API sobre D1 y los Parquet desde R2 por rangos de bytes. Corre junto a D1 (smart placement) y cachea cada respuesta una hora en el edge.

  6. 6

    Tú consultas

    Los agentes y las apps llaman a la API y reciben JSON o Markdown. En /explorar, DuckDB compilado a WebAssembly corre en tu navegador y descarga solo los trozos de Parquet que necesita tu consulta.

Decisiones que importan

SQLite para servir, DuckDB para analizar

Una ficha o una búsqueda leen pocas filas por índice: es terreno de SQLite. Una media sobre 1,6 millones de filas lee pocas columnas enteras: es terreno de un motor columnar. Usar cada uno en lo suyo es la diferencia entre milisegundos y decenas de segundos.

Postgres que no existe

El ETL original estaba escrito para Postgres. En lugar de reescribirlo, Postgres vive unos minutos al día dentro de GitHub Actions y su estado viaja como un volcado comprimido en R2. Cero servidores y el mismo código.

Identificadores que no cambian

Cada ejecución arranca una base nueva, así que los UUID aleatorios duplicarían licitaciones. Los ids públicos se derivan de claves naturales de la PLACSP (md5(entry_id)), y son idénticos en cualquier carga.

El orden de carga es un índice

D1 se rellenó en orden cronológico, así que «lo más reciente primero» es recorrer la tabla al revés, sin ordenar nada. Con texto completo, el propio índice FTS5 devuelve los resultados ya ordenados.

Upserts que no dependen del orden

Un año histórico puede cargarse después del día de hoy sin estropear nada: cada campo se queda con la versión más nueva, la fecha de publicación con la más antigua y el historial de estados se fusiona.

Parquet pensado para HTTP

El navegador pide rangos de bytes, así que hay pocos grupos de filas grandes (menos peticiones), URLs versionadas por etag (nunca se mezclan versiones) y cada rango se cachea en el edge para el siguiente visitante.
